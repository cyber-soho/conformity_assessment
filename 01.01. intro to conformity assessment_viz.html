Definition and objectives of conformity assessment

≈ 10 min · Lesson 1 of 6 · Slides 6–14

What a conformity assessment is, the vocabulary every auditor uses, and the three results an assessment must deliver.

Slide 7 Slide 8 Slide 9 Slide 10 Slide 11 Slide 12 Slide 13

Key terms to learn

Conformity assessment
Demonstration that specified requirements are fulfilled (ISO/IEC (International Organization for Standardization / International Electrotechnical Commission) 17000:2020): a structured, evidence-based comparison between what is required and what actually exists.
Requirement
A need or expectation that is stated, generally implied or obligatory; it comes from a law, a contract, a standard or an internal policy.
Control
A measure that maintains or modifies risk; the technical setting, procedure or practice intended to satisfy a requirement.
Test
The planned procedure applied to a control to collect information about it (document review, interview, observation, technical check).
Evidence
Records, statements of fact or other verifiable information produced by a test; it must be sufficient, reliable and relevant.
Finding
The result of evaluating evidence against a requirement: a conformity, a non-conformity or an observation.
Non-conformity (major / minor)
Non-fulfilment of a requirement. Major = control absent or broken down; minor = isolated lapse in a working control.
Observation
A remark that is not a non-conformity but signals a weakness or an opportunity for improvement.
Corrective action
Action that removes the cause of a non-conformity and prevents its recurrence; it is verified afterwards.
Audit trail
The chronological record (evidence files, timestamps, names) that allows a third person to reconstruct how a finding was reached.
Conformity vs compliance
Conformity = fulfilment of any requirement (ISO (International Organization for Standardization) usage); compliance = fulfilment of mandatory external obligations (laws, regulations, contracts).

Real-life example — Is the laptop’s screen-lock setting conformant?

Task
Take one written requirement — “company laptops must lock automatically after 15 minutes of inactivity” — test it on your Windows lab VM (virtual machine), keep the evidence and write the finding in the course findings-table format.
Relation
This is the vocabulary chain of Lesson 1 applied end to end: one requirement, one control, one test, one piece of evidence, one finding. Nothing else changes in a full audit except the number of requirements.
Future labs
Lab 0 (PowerShell verification on the Windows VM (virtual machine)), Lab 4 (the Configuration Audit Findings table uses exactly these columns) and the Project Section 6A.

Érable Cycles’ Acceptable Use Policy, section 4.2, states that laptops lock after 15 minutes without activity. The CIS (Center for Internet Security) Microsoft Windows 11 Benchmark expresses the same requirement as recommendation Interactive logon: Machine inactivity limit set to 900 seconds or fewer. On Windows, the setting is stored in the registry value InactivityTimeoutSecs under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System.

The test is simple: read the value, compare it with the limit, and record the result. If the value is absent, no timeout is enforced and the requirement is not fulfilled. The evidence is a text file that names the requirement, the test, the observed value, the computer and the time of collection. The finding is one row in the findings table: Finding ID · check · expected · observed · evidence · status · severity · owner.

In the audit of Érable Cycles this check would be repeated on a sample of the 45 laptops (Lesson 3 explains sampling). One non-conformant laptop out of ten sampled is a minor non-conformity; no timeout policy at all in Intune is a major one.

Code — Check-ScreenLock.ps1

Task
Read the Windows inactivity-timeout setting, compare it with the 900-second requirement, write an evidence file and append one finding row to findings.csv.
Relation
Demonstrates the Lesson 1 chain requirement → control → test → evidence → finding, and produces the first row of the Lab 4 findings table in the course format.
PowerShellCheck-ScreenLock.ps1 idle
·# Identifier of the requirement being tested; every finding must point back to a requirement ID so the audit trail is complete
1$RequirementId = "REQ-01"
·# The requirement in plain words, with its two sources (internal policy clause and CIS Benchmark recommendation) — the auditor never tests an unwritten expectation
2$RequirementText = "Laptops must lock after 15 minutes of inactivity (AUP s.4.2; CIS Windows 11 Benchmark 'Interactive logon: Machine inactivity limit' <= 900 s)"
·# The expected value expressed as a number so the comparison is objective: 15 minutes = 900 seconds
3$ExpectedMaxSeconds = 900
·# Registry key where Windows stores the policy-enforced inactivity timeout (the control under test)
4$RegPath = "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System"
·# Name of the registry value that holds the timeout in seconds
5$ValueName = "InactivityTimeoutSecs"
·# Folder where evidence files are kept; the course convention is one 'evidence' folder per lab
6$EvidenceDir = Join-Path $PWD "evidence"
·# Create the evidence folder if it does not exist; -Force avoids an error when it already exists; Out-Null hides the console output
7New-Item -ItemType Directory -Path $EvidenceDir -Force | Out-Null
·# THE TEST: read the value; -ErrorAction SilentlyContinue returns $null instead of stopping when the value is not configured
8$Observed = (Get-ItemProperty -Path $RegPath -Name $ValueName -ErrorAction SilentlyContinue).$ValueName
·# Turn the raw result into a human-readable observation; an absent value means no timeout is enforced at all
9if ($null -eq $Observed) { $ObservedText = "not configured (no timeout enforced)" } else { $ObservedText = "$Observed seconds" }
·# THE EVALUATION: conformant only if a value exists, is greater than 0 (0 disables the lock) and does not exceed 900 seconds
10if ($null -ne $Observed -and $Observed -gt 0 -and $Observed -le $ExpectedMaxSeconds) { $Status = "CONFORM" } else { $Status = "NON-CONFORM" }
·# Timestamp of collection — evidence without a date cannot be placed in the audit trail
11$Timestamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
·# Evidence file name following the course convention Lx-Enn_description_machine.txt
12$EvidenceFile = Join-Path $EvidenceDir "L0-E01_screen-lock_$env:COMPUTERNAME.txt"
·# THE EVIDENCE: write the requirement, the test performed, the observed and expected values, the result, who collected it and when
13@("Requirement: $RequirementText", "Test: read $RegPath\$ValueName", "Observed: $ObservedText", "Expected: 1..$ExpectedMaxSeconds seconds", "Result: $Status", "Collected: $Timestamp on $env:COMPUTERNAME by $env:USERNAME") | Set-Content -Path $EvidenceFile -Encoding UTF8
·# THE FINDING: one object with the columns of the Lab 4 findings table; severity is left empty for a conformity and set to Medium for this non-conformity
14$Finding = [PSCustomObject]@{ FindingID = "F-01"; RequirementID = $RequirementId; Check = "Screen-lock inactivity limit"; Expected = "<= 900 s"; Observed = $ObservedText; Evidence = (Split-Path $EvidenceFile -Leaf); Status = $Status; Severity = $(if ($Status -eq "CONFORM") { "-" } else { "Medium" }); Owner = "IT administrator" }
·# Append the finding row to the CSV table; -Append lets the next check script add its own row to the same table
15$Finding | Export-Csv -Path (Join-Path $EvidenceDir "findings.csv") -NoTypeInformation -Append -Encoding UTF8
·# Show the finding on screen so the result can be read immediately during the lab
16$Finding | Format-List

Step-by-step explanation

  1. Lines 1–3 state the requirement. Before touching the system, the auditor writes down what is required, where that requirement comes from, and the numeric threshold that will decide the result.
  2. Lines 4–5 identify the control: the exact place in Windows where the setting lives. This is what the requirement maps to on this platform.
  3. Lines 6–7 prepare the evidence folder so that every file produced by the test is kept in one known place.
  4. Line 8 is the test itself: a single read of the registry value. Nothing is modified — an auditor observes, an administrator fixes.
  5. Lines 9–10 evaluate: the observed value is translated into words, then compared with the threshold. The three conditions (exists, above zero, at most 900) are the whole logic of the finding.
  6. Lines 11–13 produce the evidence: a dated, signed text file listing requirement, test, observed and expected values. This file is what a reviewer will open to verify your finding.
  7. Lines 14–16 produce the finding as one row of the course findings table and append it to findings.csv — the same table you will fill with twelve or more rows in Lab 4.
  8. Run it on the Windows VM (virtual machine) as Administrator: open PowerShell, go to the folder containing the script, allow scripts for this session with Set-ExecutionPolicy -Scope Process Bypass, then run .\Check-ScreenLock.ps1.

Why conformity assessment matters in cybersecurity management

≈ 8 min · Lesson 2 of 6 · Slides 15–20

Five concrete reasons an organization performs conformity assessments, illustrated with the obligations and penalties that apply to Érable Cycles.

Slide 16 Slide 17 Slide 18 Slide 19

Key terms to learn

Due diligence
The reasonable, documented steps a prudent organization takes to protect the information it holds; an assessment with dated evidence is the proof of it.
Legal exposure
The penalties, orders and liabilities an organization faces when it does not meet a mandatory obligation (law, regulation, contract).
Breach notification
The legal duty to inform a regulator and affected individuals after a breach of security safeguards (PIPEDA (Personal Information Protection and Electronic Documents Act), Law 25) or a personal-data breach (GDPR (General Data Protection Regulation), 72 hours).
Regulator
The public body that enforces a law: OPC (Office of the Privacy Commissioner of Canada) (PIPEDA (Personal Information Protection and Electronic Documents Act)), CAI (Commission d’accès à l’information du Québec) (Law 25), CRTC (Canadian Radio-television and Telecommunications Commission) (CASL (Canada’s Anti-Spam Legislation)), EU (European Union) supervisory authorities (GDPR (General Data Protection Regulation)).
Contractual obligation
A requirement that binds through a contract rather than a law — PCI DSS (Payment Card Industry Data Security Standard) through the merchant agreement with the acquiring bank.
Self-Assessment Questionnaire (SAQ)
The PCI DSS (Payment Card Industry Data Security Standard) validation form a merchant completes itself; SAQ (Self-Assessment Questionnaire) A applies when all payment functions are outsourced to validated providers.
Security posture
The overall state of an organization’s controls as measured by an assessment at a given moment.
Improvement cycle
Findings → corrective actions → verification → next assessment; measurement is what turns activity into improvement.

Types of audits and assessments

≈ 10 min · Lesson 3 of 6 · Slides 21–27

Who performs an assessment, with what independence and what output — and the seven principles every auditor follows.

Slide 22 Slide 23 Slide 24 Slide 25 Slide 26

Key terms to learn

Audit
Systematic, independent and documented process for obtaining objective evidence and evaluating it to determine the extent to which the audit criteria are fulfilled (ISO (International Organization for Standardization) 19011).
First-party (internal) audit
Performed by the organization on itself for self-knowledge and preparation; credible to management, not to outsiders.
Second-party audit
Performed by an interested party, usually a customer auditing a supplier before or during a contract.
Third-party audit
Performed by an independent body with no stake in the result (certification body, PCI QSA (Qualified Security Assessor)); the result is a certificate or an attestation.
Regulatory audit
Performed by a public authority (OPC (Office of the Privacy Commissioner of Canada), CAI (Commission d’accès à l’information du Québec), CRTC (Canadian Radio-television and Telecommunications Commission)); it can lead to binding orders and penalties.
Attestation / declaration / certification
Attestation = formal statement that requirements are fulfilled; declaration = attestation by the organization itself; certification = attestation by a third party.
Point-in-time vs continuous monitoring
Point-in-time: the state on the day of the test. Continuous: automatic, repeated re-evaluation between audits.
The seven audit principles (ISO 19011)
Integrity, fair presentation, due professional care, confidentiality, independence, evidence-based approach, risk-based approach.

The role of conformity assessment in continuous improvement

≈ 8 min · Lesson 4 of 6 · Slides 28–34

What happens to findings after the audit: the PDCA (Plan–Do–Check–Act) cycle, ISO/IEC (International Organization for Standardization / International Electrotechnical Commission) 27001 clauses 9 and 10, corrective actions and the comparison with historical results.

Slide 29 Slide 30 Slide 31 Slide 32 Slide 33

Key terms to learn

PDCA
Plan–Do–Check–Act: the management cycle in which the conformity assessment is the Check step.
ISO/IEC 27001 clause 9 — Performance evaluation
9.1 monitoring, measurement, analysis and evaluation; 9.2 internal audit at planned intervals by objective auditors; 9.3 management review by top management.
ISO/IEC 27001 clause 10 — Improvement
10.1 continual improvement; 10.2 nonconformity and corrective action (react, find the cause, act, review effectiveness, update, document).
Root cause
The underlying reason a nonconformity occurred; removing it prevents recurrence.
Correction vs corrective action
Correction fixes the instance (encrypt one laptop); corrective action removes the cause (enforce encryption for all deployments).
Verification of effectiveness
A re-test proving the requirement is now fulfilled; a corrective action is finished only when verified.
Historical comparison
Comparing this assessment’s results item by item with the previous one: improved, unchanged or regressed.
Conformity rate
Items conform ÷ items tested, per domain; a simple indicator tracked from one assessment to the next.
